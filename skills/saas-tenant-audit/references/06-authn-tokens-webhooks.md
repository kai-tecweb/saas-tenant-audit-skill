# 06 — Authentication, tokens, password reset, webhooks

Contents: sign-in and brute force · password rules · reset flow · sessions and tokens ·
account changes · webhooks and external events · secrets and fail-closed

## Sign-in and brute force

- Limiter key: identifier (normalised, lower-case) + real client IP, with a modest count
  per minute. Consider a **per-IP ceiling too**: a composite key lets one IP spray many
  identifiers. State the residual risk (shared NAT, distributed attack). (FL-16, FL-20)
- Generic failure message and equal timing for "unknown user" and "wrong password".
- Lockout that an attacker can trigger against a victim is itself a DoS; prefer throttling
  by (identifier, IP) over global per-account lockout.
- Check that the login path is actually throttled (tests often only cover the new
  endpoints).

## Password rules

- Minimum length (12+), no composition rules required; check against a breached-password
  service using a k-anonymity API (only a hash prefix leaves the server). Choose a short
  timeout and decide the failure mode explicitly (usually fail-open for availability,
  documented).
- Apply on sign-up, change and reset. Login does not re-validate (do not force-lock
  existing users).

## Password reset (test each item)

- Same response and comparable timing whether the e-mail exists or not (do the same hashing
  work for unknown addresses). Send mail through a queue so send time is not visible.
- Token: generated by the framework's broker, stored hashed, short expiry (e.g. 60 min),
  **single use**, a new request invalidates older links.
- Invalid, expired and e-mail-mismatch cases return the **same** error.
- Successful reset: revoke all existing sessions/tokens; mark the address verified if
  appropriate; apply the password rules.
- Rate limit request and consume endpoints separately (per IP+identifier and per IP).
- Reset link host comes from configuration, never from the request `Host` header
  (host-header poisoning).

## Sessions and API tokens

- **Blast radius of the setting (FL-19).** Two settings that both say "tokens expire" can
  differ: a global expiry evaluated against every token's creation time invalidates all
  old tokens at once; a per-token `expires_at` applies only to newly issued ones. Ask
  "does this apply to existing records or only new ones?" and choose the variant the
  requirement needs, then prove it with a fixture that looks like the old data (created
  long ago, no expiry).
- Understand the app's own session model before designing "other device" tests: if login
  deletes all tokens (single-session), "revoke others on password change" tests will
  mislead. Print the fixtures' state before the change (FL-07).
- Expired token → 401 and the client must redirect to login (test the UI path).
- Admin/service tokens: scope (abilities) rather than all-powerful; prune expired tokens
  on a schedule.
- Logout revokes server-side, not just client-side.

## Account changes

- Changing the e-mail address must require the current password and reset verification
  status; consider notifying the old address.
- Changing the password revokes other sessions.
- Profile update must not accept role/tenant/plan fields (mass assignment).
- Account deletion: define what is deleted, when, and that public surfaces disappear
  (lifecycle table in `03`).

## Webhooks and external events (FL-18, FL-28, FL-30)

- **Signature verification with the provider's official routine, fail-closed.** If the
  signing secret is unset/empty, reject with a 5xx; many libraries will happily compute an
  HMAC with an empty key, which anyone can forge. Test with a signature computed from the
  empty key.
- Verify against the **raw body** exactly as received (a JSON re-encode breaks it;
  proxies must not rewrite the body).
- **Idempotency**: store event ids; treat only `processed` as duplicate; allow
  re-processing of `failed` and of `received`-but-stale events; guard concurrent
  redeliveries with a conditional update so exactly one worker proceeds.
- **Null-guard every update keyed by an external id.** If the id cannot be extracted (the
  provider moved the field in a new API version), an ORM `where(col, null)->update(...)`
  becomes `IS NULL` and updates *every row with an empty column* — in the field this
  flipped many unrelated rows to a failing state at once. Return early when the id is
  missing/empty; add a test where the field is absent.
- Provider API versions move fields; read with fallbacks and skip (do not guess).
- Verify purchases/sessions belong to the caller's tenant; avoid "already recorded →
  success" branches ahead of the owner check (existence oracle).
- Send test events only signed and harmless; delete the event rows afterwards. Use the
  **real feature path** when possible: a direct DB edit hides preconditions that the real
  path exposes (FL-30).

## Secrets and fail-closed defaults (FL-18, FL-23)

- Every check that depends on a configured secret must have an explicit *empty/unset →
  reject* branch and a test with the empty value.
- Internal endpoints protected by a shared secret (cache revalidation, cron triggers,
  metrics) should return 503 when the secret is unset and 403 on mismatch, validate input
  strictly, and — better — not be reachable from outside at all (see `07`).
- Allow-list regexes: test with newline, NUL, unicode, over-length input. In PHP `$`
  matches before a trailing newline; use `\z`. Prefer explicit character classes.
- Rotating a leaked secret is not done until it has been tried against **every** store
  where the same string could be valid (database root, other apps, tokens, deploy scripts)
  and cleaned from where it was written (history, docs, config backups, chat logs).
