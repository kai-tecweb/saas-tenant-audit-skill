これらのエントリは、マルチテナント SaaS の実際の監査・修正キャンペーンで**実際に犯した誤り**に由来し、件数・正確なステータスコード・独立レビューによってのみ発見されたものです。抽象化してあり、名前・ホスト・データは含みません。出典タグ: **[field]** = キャンペーンで観測したもの、**[std]** = キャンペーンで裏付けられた標準的な実践。検証スクリプトを書く*前に*、A 節と B 節を読んでください。

使い方: **症状**の行は 1 つのキャンペーンの具体例（特定のフレームワーク、トークン形式、言語の癖）です。**対処**の行はスタックに依存しません。逸話ではなく対処を適用してください。F 節（運用）は、サーバーも運用している場合に特に重要で、マネージドホスティングだけが対象なら読み飛ばして構いません。各教訓は 1 つのキャンペーンに由来するため、頻度の証拠ではなく、有力なヒントとして扱ってください。

## A. テスト設計

### FL-06 期待値を実測値の隣に表示する。正確なステータスをアサートする [field]
- **症状:** あるスクリプトは、404 になるべきリクエストが 429（リミッターがハーネスを捕捉した）だったのに「ブロックされた」と報告しました。別のスクリプトは、認可が検証より先に走るため、空のボディで 403 チェックを通過しました。
- **原因:** 「何らかの拒否が起きた」は、多くの誤った理由でも成り立ちます。
- **対処:** リクエストごとに 1 行、`label | expected=404 actual=404` の形で出します。正の結果もアサートします（単に「403 ではない」ではなく `allowed → 200/201`）。キーワード引数、またはリクエストボディを検証するヘルパーを使います。位置引数のヘルパーは気づかないうちに入れ替わります。

### FL-07 前提条件をアサートする [field]
- **症状:** 失効テストが `before: 401 401 / after: 401 401` と出力し、成功のように見えました。「before」が誤りでした。ベアラートークンを保持する状態ファイルが `source` されており、トークンには `|` が含まれていたうえ、途中のログインがすべてのトークンを失効させていたのです（シングルセッションのアプリ）。
- **対処:** `before == expected` をアサートし、派手に失敗させます。フィクスチャは JSON か `printf %q` で保存し、`source` は使いません。共有状態を変更するヘルパー（ログイン、ログアウト、リフレッシュ）は、ステップの順序を決める前に一覧にします。先にアプリのセッションモデルを把握します。

### FL-08 不在の確認にはすべて正の対照が必要 [field]
- **症状:** 「重複メールはキューに入っていない」が True と出力されました。テストが自分のセッションを消してしまっており、リクエストがテスト対象のコードに届いていなかったためです。
- **対処:** 負の結果と同じ行で、トリガーとなるステップが実行されたこと（正確なステータス／コード）をアサートします。正の対照が通るまで、負の結果は未証明として扱います。

### FL-10 陳腐化した回帰スクリプトは誤った判定を出す [field]
- **症状:** インフラ変更の後、古いエンドツーエンドのスクリプトを回帰チェックとして再実行しました。プロダクトの契約がその後変わっていた（必須ヘッダー）ため全面的に失敗し、本番ログにも不要な ERROR を書き込みました。
- **対処:** 再利用の前に、スクリプトの前提を現在の契約と突き合わせます。その領域を扱う最新のスクリプトを優先します。テスト自身が出力したログ行がどれかを報告に記載します。

### FL-11 既存の制御を改善する前に、まずテストする [field]
- **症状:** 有料機能の月間利用上限を競合に対して堅牢化しようとしていました。保存された数値を読み戻すと、カウント対象のカラムが常に 0 でした（マスアサインメント保護が黙って落としていた）ため、旧上限は一度も何も制限していませんでした。
- **対処:** まず検証用テナントで*既存の*ガードを上限超過まで叩き、保存された数値を読みます。別の場所で書かれるログの合計より、ガード自身がインクリメントするカウンタを優先します。「カラムは存在するがモデル経由では書き込めない」状態は危険信号として扱います。

### FL-30 実際の機能経路を通す [field]
- **症状:** データベースの編集では「うまくいった」一方、プロダクト自身のゲート付きフローを通すと、本番全体に及ぶ Webhook のバグ（`FL-28`）が露呈しました。
- **対処:** 実際の経路を優先します。近道は、隠れた前提条件に関係なく成功してしまいます。

## B. テストデータの衛生管理

### FL-05 失敗を隠さないクリーンアップ [field]
- **症状（3 回）:** クリーンアップとセットアップの手順をマーカー行の `grep` にパイプしていました。致命的なデータベースエラーが*空の出力*を生み、「報告事項なし」に見えました。セットアップが途中で失敗し、クリーンアップは組織を処理したがユーザーは処理せず、外部キーが削除を阻んだのに何も知らせませんでした。残った行はベースラインの件数でしか見つかりませんでした。
- **対処:**
  1. セットアップとクリーンアップの**生の**出力を表示します。そこでは `| grep` も `2>/dev/null` も使いません。
  2. 先へ進む前に、セットアップが空でない ID を返したことをアサートします。
  3. セットアップが触れる**すべてのテーブルでプレフィックス**によりクリーンアップします（履歴テーブルなどの外部キーの持ち主、ジョブが作成する行などの非同期の書き込み元、キャッシュ、スロットルカウンタを含む）。セットアップが実際に何を作ったかには依存させません。
  4. クリーンアップは終了時だけでなく**開始時**にも実行します（kill されたり止まったりした実行はフィクスチャを残します）。
  5. **ベースライン一致**の確認（テーブルごとの件数が前後で一致）で終え、一致しなければ失敗させます。
  6. 他のアクターがデータベースを共有している場合は、テスト所有のサブセットで件数を比較します。

### FL-09 自分のトラフィックも対象の防御の対象になる [field]
- **症状:** ハーネスのリクエストが IP ごとのリミッターに引っかかり、404 が期待される箇所で 429 と報告されました。カウンタをリセットするため共有キャッシュテーブルを消すと、テストに必要なログインセッションまで消えてしまい、後続の手順が誤った理由で失敗しました。
- **対処:** リミッターのウィンドウを実行計画に組み込みます。セクションごとにリセットします。リセットするストアに他に何が入っているかを把握し、再作成します。可能な限り新しい識別子を使います。レート制限のウィンドウを空けてスイートを実行します。

### FL-12 テストツールがプロダクトのバグに化ける [field]
- **症状:** CDN が HTTP ライブラリのデフォルトの User-Agent に 403 を返しました。シード行が無効な enum 値を使っていました。スイートを 1 分以内に 2 回実行するとリミッターに引っかかりました。前の手順で残ったテストユーザーが件数をずらしました。
- **対処:** ブラウザ相当の UA を使い、その旨を記録します。フィクスチャをスキーマに対して検証します。実行のたびに件数のスナップショットを取り、不一致は以前の手順の残骸として扱います。

### FL-34 PID で kill する。自分自身に一致しうるパターンで kill しない [field]
- **症状（2 回）:** プロセス kill のパターンが、それを含むシェルのコマンドラインにも一致し、セッションを kill しました。言語組み込みサーバーで起動したヘルパーサーバーは、親を kill した後もフォークされたワーカーが生き残りました。
- **対処:** 起動時に PID（`$!`）を取得して、それを kill します。バイナリはフルパスで照合します。クリーンアップの後、待ち受けポートが閉じていることを確認します。同じ失敗が繰り返されるときは、注意喚起ではなく、誤りを不可能にするツール（ラッパースクリプト）にルールを置き換えます。

## C. ツールと環境

### FL-14 ボット対策ウィジェットのテスト [field]
- 自動化によって起動されたブラウザ（ヘッドレスまたは操作されるもの）は、ウィジェットに正しく拒否されることが多くあります（チャレンジ失敗のエラーコード）。通常どおり起動し、リモートデバッグポート経由でアタッチしたブラウザは通過します。ベンダーの**エラーコード**により、「設定ミス（ホスト名が未登録）」と「自動化として検出された」を区別できます。
- ウィジェットの iframe はシャドウ DOM 内にあります — 隠しのレスポンス入力フィールドに対してアサートします。
- 成功経路と同じくらい意図的に**失敗経路**をテストします。欠落、偽造、再利用、別アクション用のトークン、ベンダー障害（フェイルクローズでなければならない）。

### FL-31 ローカルのランタイムに拡張がないとき [field]
- ローカルの PHP には HTTP 拡張と一部の XML/DOM/mbstring 拡張がなく、本物のテストランナーも本物のクライアントも動かせませんでした。自作のランナーは、本物のランナーの分離規則（テストごとに新しいアプリケーション）を再現しなければ、状態リークのバグを隠してしまいます。本物のクライアントのピン留め／中断の挙動は、実ホスト上の検証用ハーネスで確認しなければなりません。

### FL-35 公表している制限を測定する [field]
- 移行計画をきっかけに*現在の*アップロード上限を測定したところ、開発サーバーのランタイム設定が、検証で公表している上限よりずっと小さい値しか許可しておらず、通常のアップロードが黙って失敗していました。公表している各制限は、それを実際に強制するレイヤー（プロキシのボディサイズ、ランタイム設定、フレームワークの検証）に対してテストし、隠れた契約を保ったままの移行を選びます。

## D. 認可監査の手法

### FL-01 3 つの視点（静的な読解、独立した再スキャン、ライブのマトリクス） [field]
- 認証済みAPI全体をルートごとに読んで、欠陥の大半が見つかりました。残りのいくつかは、「ID を受け取るすべてのメソッド」を再スキャンするよう指示された独立レビュアーと、被害者のデータの前後を比較する 2 テナントのライブマトリクスによって初めて見つかりました。
- **対処:** 3 つすべてを実行します。2 人目のレビュアーには、1 人目と異なる観点を与えます。

### FL-02 JSON ボディと保存済みフィールド内の ID [field]
- レイアウトドキュメントが任意のリソース ID を受け付けていました。姉妹の「アイテム追加」エンドポイントはスコープされていたため、対策済みに*見えました*が、匿名の読み取りがそれらの ID をテナントや公開状態のフィルタなしで解決しており、データフィールドを通じたテナント間のメタデータ漏洩になっていました。
- **対処:** 保存されたすべての参照を、書き込み時に検証し、読み取り時に再検証すべき入力として扱います。

### FL-03 存在オラクル [field]
- 「記録済み → 成功」が所有権チェックより前に走っていました。「見つからない」と「あなたのものではない」が異なるステータスを返していました。スコープ付きクエリが、合意した規約では 404 のところで `200 null` を返していました。
- **対処:** 拒否の規約を合意してテストします。他テナントの ID と存在しなかった ID の応答を比較します。

### FL-04 状態はすべてのエントリポイントで守るべき不変条件 [field]
- 論理削除が `status='published'` を残したため、後から追加された公開書き込みエンドポイント（フォーム送信、予約、決済など）のすべてが、削除済みのアイテムに対して動き続けました。
- **対処:** 状態 × エントリポイントの表（`03`）を作ります。削除で入口を閉じます。ジョブとキャッシュも確認します。不変条件は対照との相対で表現します（「存在しなかったものと区別がつかない」）— あるエンドポイントは「未設定」に対して正当に `200 null` を返しており、最初の期待値（404）は誤りでした。1 つのキャッシュ利用側で緑になっても、他の利用側については何も言えません（動的ルートと事前レンダリングされたサイトマップ）。共有キャッシュに書き込むテストは、そのキャッシュも片付けなければなりません。

### FL-29 到達可能性が変えるのは優先度であり、存在ではない [field]
- 順位付けの前に、UI のエントリポイントと実際の利用を確認します。API が完全で UI の呼び出し元がない機能は、実在する攻撃面ですが優先度が異なります。棚卸しでは、各主張がどのレイヤーに基づくか（ルートが存在する／UI が接続している／実利用がある）を示すべきです。

### FL-13 ステータスコードが証明するのは到達性であり、正しさではない [field]
- 「リンクはまだ動くか?」のチェックが HTTP ステータスしか見ておらず、その間にプロキシの変更がすべてのテナントのルートページをマーケティングサイトに置き換えていました。テナントごとに異なるはずのものは、内容の同一性を検証します。完全一致のパスは、すべてのホストに共有されるものとして扱います。

### FL-26 エージェントは同じ発見事項を異なる重大度で評価する [field]
- 並列の読み取り専用の監査エージェントが、ある発見事項を異なる重大度で評価しました。無害な確認用リクエストを 1 つ送るだけで決着しました。読み取り専用の指示書のせいで、エージェントが教訓の記録を飛ばすこともありました。
- **対処:** オーケストレーターが、各候補を最小限のリクエスト 1 つで検証します。評価を平均しません。指示書には、誰が観察を記録するかを明記し、エージェントは候補を報告するよう伝えます。

### FL-28 外部 API はフィールドを動かす [field]
- プロバイダーの新しい API バージョンがフィールドを移動しました。ハンドラは `where(col, null)->update(...)` を実行し、関係のない多数の行を、失敗する課金状態に切り替えてしまいました。**対処:** 外部 ID をキーにした `update()`／`delete()` の前に null／空のガードを入れます。フォールバック付きで読み取ります。フィールドが欠けたペイロードをテストします。

### FL-16 制限を安全にテストする [field] — `04` を参照

### FL-18 フェイルクローズ。忘れられた文字をテストする [field]
- 空の Webhook シークレットは、空のキーで有効な HMAC を計算します。ある言語では正しい slug の正規表現が、別の言語では末尾の改行に一致しました（`$`）。**対処:** 未設定なら拒否する分岐を明示し、空のシークレットを使ったテストを用意します。許可リストのテストには、改行、NUL、Unicode、長さ超過を含めます。

### FL-19 セキュリティ設定の影響範囲 [field]
- グローバルなトークン有効期限の設定は、既存のすべてのトークンを一度に無効にするところでした。トークンごとの有効期限は新しいものにしか適用されませんでした。「既存のレコードか、新規のみか?」を問い、旧形式のフィクスチャでテストします。

### FL-20 ヘッダーを信頼するのは、書き込んだ側が偽装できない場合だけ [field] — `07` を参照

### FL-27 以前の堅牢化が後の機能を制約する。限界を明記する [field]
- 先に設定されたフレーム拒否ヘッダーが、埋め込み可能なリレーページをどこに置けるかを決めました。ウィジェットの DOM が隠されていたため、セレクタベースのテストが通用しませんでした。各制御の残存リスクを報告に明記します（Origin チェックは、ブラウザ以外のクライアントを止めません）。

## F. 運用と引き継ぎ（手渡し）

### FL-21 経路を閉じる前にすべての呼び出し元を見つける [field]
- キャッシュパージのエンドポイントを外部からブロックしようとしましたが、サーバー自身が公開 URL 経由でそれを呼んでいました。**対処:** 先に呼び出し元（自己呼び出しを含む）を見つけ、内部アドレスへ移してから、ブロックします。クライアントとサーバーが対になる変更では、安全な側を先に本番反映し、シークレットを先に入れます。保護するすべてのエンドポイントの呼び出し元を棚卸しします。

### FL-22 「停止した」とは、起動経路が 1 つも残っていないこと [field]
- そのアプリには、名指しされたもの以外にも複数のスーパーバイザー（プロセスマネージャー、スケジューラー、サービスユニット）があり、デプロイのヘルスチェックは本来の対象とは別のアプリをテストしていました。

### FL-23 漏洩したシークレットは、入力された場所ならどこでも有効 [field]
- 古いパスワードの使い回し先を検索したところ、一致した行が出力されましたが、それが*まさにシークレットそのもの*でした（履歴の 1 行に、誤入力されたシークレットだけが書かれていた）。同じ文字列は、他の認証情報ストアでも通用しました。
- **対処:** 件数、ファイル名、キー名だけを報告します。それが**保存された**場所と、それが**通用する**場所を検索します。

### FL-24 `sudo -n -l` ではパスワード不要を証明できない [field]
- 「許可」と報告し、パスワード付きの許可も含みます。NOPASSWD を証明するには、無害なコマンドを `sudo -n` で実行します。

### FL-25 追跡されず ignore もされていないシークレットのバックアップ [field]
- 本番の環境ファイルのバックアップが、リポジトリの作業ツリーに置かれたまま ignore もされておらず、稼働中のものと同一のシークレットを保持していました。名前とハッシュで棚卸しし、削除の前に明示的な了承を得て、穴を塞ぎます（env ファイルの派生形に対する ignore ルール）。

### FL-32 引き継ぎ（手渡し） [field]
- 特権コマンドが、どのマシン／アカウントで実行するかを示さずにユーザーへ渡されました。ファイルは別のホストにあったため、「見つからない」となりました。
- **対処:** 引き継ぎのたびに、実行場所（ホスト + アカウント + そこへの到達方法）を明記し、絶対パスを使い、「マシンが違う」と「ファイルがない」を切り分ける 1 行のチェックを含め、ロールバックを最初に示します。

### FL-33 必要のないシークレットを持ち回らない [field]
- シークレットが必要な手順では、ユーザーに 1 行の対話式コマンドを渡します。その後、読み取り専用で検証します。設定の書き換えは、触れる前にロスレスであること（diff）を証明します。バックログは、次のセッションが見つける場所に書き留めます。
