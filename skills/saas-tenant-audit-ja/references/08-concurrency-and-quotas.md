# 08 — 競合・制限・クォータ

「トランザクション内にある」「単一のステートメントである」ことは証拠になりません。並行処理の修正が検証済みと言えるのは、
**同じテストで、修正前の版が目に見えて壊れる**場合だけです。(FL-17)

## 主張ごとに使うプリミティブ

| 主張 | プリミティブ | 備考 |
|---|---|---|
| 「最大 N まで」（ちょうど 1 を消費） | 条件付きUPDATE 1 文 `UPDATE ... SET used = used + n WHERE used + n <= limit`。成功 = 影響行数 1 | カウンタ行はトランザクションの*前に*（外で）存在させておく |
| 「残りのうち最大 N まで付与」 | トランザクション内の行ロック（`SELECT ... FOR UPDATE`）で `min(N, limit - used)` を計算 | 先に行を存在させておく。既存行への `INSERT IGNORE` は共有ロックを取り、排他ロックと同じトランザクション内で行うとデッドロックを招く |
| 「1 つのワーカーだけが処理する」 | 取得済み状態への条件付きUPDATE、またはキューへ解放し直さないリソース単位の重複実行防止ジョブロック | ジョブ側でもリソースの状態を再読み込みさせる |
| 「2 つの書き込み元から JSON ドキュメントへマージ」 | 行ロック + 読み取り・変更・書き込み、または空のままのキーだけを書き込む | 素朴な読み取り・変更・書き込みは更新を失う |
| 「テナント間で一意」 | データベースの一意インデックス（アプリケーションの事前チェックではない） | 事前チェックは競合状態を起こす |

エンジンごとの注記: 同じ基本操作は他のエンジンにもあります。PostgreSQL: 行の存在保証は `INSERT ... ON CONFLICT DO NOTHING`、条件付き消費は `UPDATE ... WHERE used + n <= limit`、ロックは `SELECT ... FOR UPDATE`（分離レベルによって再読み込みで見える内容が変わります）。Redis: アトミックな `INCR` とLuaスクリプト、または `SET NX` で確保します。

カウンタ: ガード内でインクリメントします。返却は、ガード対象の処理が失敗した場合**のみ**行います。削除時にデクリメントしません。

## 検証手順

各修正について、実際のデータベースエンジン上の検証用テナントに対して実行します。

1. **並列実行** — 上限 L に対して N 個（N > L）の同時リクエストを送ります。成功はちょうど L 件になるはずです。
2. **素朴な対照** — 旧実装（または意図的にロックを外した版）に対して*同じ*テストを実行します。更新の喪失または過剰付与が現れなければなりません。現れない場合、そのテストではバグを検出できません。
3. **両方の数値を報告**します（「上限 5 に対し 12 並列 → 5 件成功、対照 → 9 件」）。
4. 「最大 N まで付与」型では、N を残量より大きくして繰り返し、一部だけ付与されることを確認します。
5. **副作用が重複しない**ことを確認します。メール 1 通、ベンダー呼び出し 1 回、行 1 件のみであること。

## スケールの前提 (FL-17)

レプリカを増やすと、インスタンスが 1 つだけの時にしか成り立たなかった前提が、気づかないうちに崩れます。ワーカーを増やす前に、タイムアウト・リース・ロックの TTL をすべて洗い出して比較します。

- キューの `retry_after`／可視性タイムアウトは、**最長のジョブタイムアウトより大きく**しなければなりません。そうでないと、実行中のジョブが別のワーカーへ再配信されます（重複実行）。旧値より長いジョブを流し、`attempts` が 1 のままであることで証明します。
- ジョブの重複実行防止ロックと一意ロック、スケジューラの `onOneServer`、共有されないキャッシュ上のキャッシュベースのロック。
- ロックやカウンタとして使われているプロセス内キャッシュや静的な状態すべて。

この比較は、ジョブクラスをリフレクションで走査するユニットテストとして表現します。

## 確認すべき「読んでから処理」の罠 (TOCTOU)

- プラン上限のための「既存の件数を数えてから作成」（並列リクエストが並列度の分だけ上限を超える）。
- 「残高／クォータを確認してからベンダーを呼び、記録する」（先に記録するか、先に確保する）。
- トークン／リンクの「検証してから使用」（1 回限りは、事前の読み取りではなく削除／更新で強制しなければならない）。
- 識別子ごとのセッション作成の上限。

## 負荷テストの衛生管理

数十リクエスト、検証用テナント、ベンダー呼び出しなし（またはスタブ経路）とし、終了後にカウンタと行を片付けます。自前のレート制限がテストを抑制することがあります。セクションの間でカウンタをクリアするか、新しいキーを使ってください。(FL-09)
