# 02 — 2テナントのブラックボックスマトリクス（監査の中核）

目次: セットアップ · マトリクス · 各行で変化させるもの · 存在オラクル · データの中に隠れたID · 管理者ゲート · 合否のルール · 三重のレンズのルール · 行の例

## セットアップ

- **テナントA**（攻撃側）と**テナントB**（被害側）を、それぞれユーザー1人で、製品の通常のサインアップ経路を使って作成します。サインアップが保護されている場合（CAPTCHA、メール確認）は、所有者が許可する方法で作成し、その旨を*明記*してください。時間を節約するために、公開経路の保護を回避してはいけません。
- Bには、関連する状態ごとに1つずつ、一式のフィクスチャを用意します。通常のリソース、公開済み／パブリックなもの、下書き、論理削除されたもの、子（ネストしたリソース）を持つもの、アップロードされたファイルを持つもの、外部リンク／URLフィールドを持つもの、そして製品が持つ課金／プランのオブジェクトです。
- BのIDと、**Bのデータのスナップショット**（行数と、フィクスチャの行のハッシュまたはダンプ）を記録します。書き込み系のプローブのたびに、これと比較します。
- Aのセッション／トークンを取得します。あわせて、未認証のクライアントと、製品にあればAのテナント内の低権限ユーザーも用意しておきます。
- **対照**を追加します。実在したことのないID（実際のIDと同じ形式のもの）です。
- **スナップショットの方法。** 検証用環境を自分で所有しているなら、Bの行をデータベースからスナップショットします。顧客レベルのアクセスしかない場合（純粋なブラックボックス）は、API経由で取ります。前後でBの一覧・詳細エンドポイントを*Bとして*読み、比較します。どちらの方法かを明記してください。API経由のスナップショットでは、APIが隠しているフィールドは見えません。

## マトリクス

IDを受け取る、またはテナントのリソースに作用するインベントリの各行について、次を実行します。

| Actor | Target | Expected |
|---|---|---|
| A (valid token) | A's own resource | success (positive control — proves the request is well-formed) |
| A | B's resource | the product's denial convention (e.g. 404) |
| A | never-existed ID | **same response as the line above** |
| anonymous | B's resource (protected route) | 401 |
| A (non-admin) | admin-only route | 403 (or the convention) |
| B's low-privilege user | B's owner-only route | 403 |

各行を `METHOD path | actor | expected=<code> actual=<code> | body-shape` の形式で出力します。書き込み・削除系のプローブのたびに、Bのスナップショットの差分を確認します。拒否されたリクエストがBのデータを変更していた場合は、ステータスが正しく見えても、重大な指摘事項です。（FL-06）

**拒否の規約**は、先に所有者と合意します（通常は、存在を明かさないよう「自分のものではない」に対して404）。「データが返らなかった」だけを見るのではなく、規約に沿っているかをテストしてください。（FL-03）

## 各行で変化させるもの

1. **パスのID** — BのIDに差し替えます。
2. **クエリパラメータ** — `?id=`、`?tenant=`、`?owner=`、フィルタ、include、ソートキー。
3. **JSONボディのフィールド** — IDに見えるすべてのフィールド: `parent_id`、`template_id`、`resource_ids[]`、`owner_id`、`tenant_id`、ネストした配列、保存済みのJSONブロブ（他のリソースのIDを並べたメニューやレイアウトのドキュメントなど）。（FL-02）
4. **マスアサインメント** — サーバー側で制御されるべき追加のフィールド（`tenant_id`、`status`、`is_admin`、`price`、クォータのカウンター）を送ります。レスポンス「と」保存された行の両方を確認します。（FL-11、スタック別メモ）
5. **一括／一覧のエンドポイント** — テナントで絞り込んでいるか、テナント「と」状態の両方で絞り込んでいるか。ページネーション／カーソルや検索で、他のテナントの行や件数が漏れないか。
6. **ネストしたルート** — `/parents/{p}/children/{c}`: `c` が `p` に属し、「かつ」`p` がテナントに属することが検証されているか。組み合わせの不一致は典型的な抜け穴です。
7. **同じパスでの異なる動詞** — GETはスコープされているがPATCH/DELETEはされていない（またはその逆）。HEAD/OPTIONSや古いAPIバージョンも対象です。
8. **アップロードとダウンロード** — Aは、パスを推測してBの保存済みファイルを取得できるか。ファイルのURLは推測不能か、また必要な箇所で認証されているか。
9. **リソースをまたぐサイドチャネル** — エクスポート、請求書、Webhook、監査ログ、検索候補、アナリティクス、通知。
10. **IDを解決する公開エンドポイント** — テナントのデータに保存されたIDを参照解決する匿名エンドポイントは、*他の*テナントのメタデータを漏らす可能性があります（FL-02）。
11. **機能URL（秘密のリンク）** — URL中の推測できないトークンだけで守られているページやダウンロード（支払いリンク、共有リンク、パスワードリセットのリンク、署名付きファイルURL）。確認すること: トークンの長さ・エントロピーと、連番IDから導出していないこと。有効期限と失効。リソースを削除・無効化したらリンクも無効になること。CDNに公開キャッシュされないこと。`Referer`やログ経由でトークンが漏れないこと。

## 存在オラクル（FL-03）

「見つからない」と「自分のものではない」の間で次のいずれかが異なる場合、攻撃者はリソースが存在することを知ることができます。

- ステータスコード（404、403、null付きの200）、
- レスポンスボディやエラーメッセージ、レスポンスの*形*、
- 応答時間（追加の検索による）、
- 所有権チェックの「前」に置かれた「記録済み → 成功」のような早期リターン、
- 検証エラーの違い（外部のIDに対する422は、そのIDが検索されたことを意味します）。

他人のIDと存在しないIDのレスポンスを、バイト単位で比較します（ステータス、ボディの形、注目すべきヘッダー）。両者は区別できてはいけません。

## データの中に隠れたID（FL-02）

他のリソースへの参照を*保存する*すべてのフィールドを確認します。レイアウト／メニューのドキュメント、「関連アイテム」、保存済みフィルタ、共有リスト、ワークフローのステップなどです。それぞれについて2つの問いがあります。

1. **書き込み**時: 参照されているすべてのIDが呼び出し元のテナントに属することを、サーバーは検証しているか。（兄弟のエンドポイントがスコープされていても、このエンドポイントがそうであるという証明にはなりません。）
2. **読み取り**時、特に匿名の読み取り: それらのIDを解決するときに、サーバーはテナントと状態（公開済み、未削除）を再チェックしているか。

## 管理者とロールのゲート

- 全テナントのデータを返すすべてのルートには、明示的な管理者ゲートが必要です。Aの通常のトークンでテストします。また、管理者「UI」のデータソースもテストします（ゲートが欠けた通常のルートを呼んでいることがあります）。
- なりすまし／「ユーザーとして表示」やサポート用ツールを確認します。
- プロフィール更新やサインアップを通じて設定できるロールフラグは、権限昇格（マスアサインメント）です。

## 合否のルール

- 次のいずれかに該当する場合は不合格とします。Bのデータが返った、Bのデータが変更された、他人のIDと存在しないIDで応答が異なる（所有者が別の規約を受け入れた場合を除く）、Aが管理者ルートで成功した、401が期待される箇所で認証なしで成功した。
- 正の対照を用意できなかった行は「未テスト」とし、レポートに記載しなければなりません。
- すべての不合格は、指摘事項にする前に、フィクスチャをクリーンに再構築した上で一度再実行し、検証スクリプトの誤りを除外します。（FL-06, FL-10）

## 三重のレンズのルール（FL-01）

各ハンドラーを読んでテナントのフィルタを探すだけでは、実戦では抜け穴の一部しか見つかりませんでした。残りは、(a) 「別の枠組みで」「IDを受け取るすべてのメソッド」を再スキャンするよう指示された、独立した二人目のレビュアーと、(b) 前後のスナップショットを使ったこのブラックボックスマトリクスによって見つかりました。三つすべてを使ってください。静的な読み取り、独立した再スキャン、実環境でのマトリクスです。`12-orchestration.md` を参照してください。

## 行の例（一般形）

```
PATCH /api/v1/projects/{id}/items/{itemId}
  A→own/own      expected=200 actual=200 shape=ok           (control)
  A→B/B          expected=404 actual=404 shape=notfound     PASS
  A→A/B-item     expected=404 actual=200 shape=ok           FAIL: item not tied to parent  (B snapshot changed: yes)
  A→never/never  expected=404 actual=404 shape=notfound     control matches B row
```
