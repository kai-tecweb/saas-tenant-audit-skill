# 05 — SSRF（サーバーサイドリクエストフォージェリ）とその他のアウトバウンドリクエスト

目次: シンクの洗い出し · 単一のガード付きフェッチャーの設計 · テスト項目 ·
対象の HTTP 拡張がない環境での検証

## 1. 名指しされた箇所だけでなく、すべてのシンクを探す (FL-15)

監査指摘は通常、1つの関数（「ユーザーの URL を取得する」）を名指しします。アウトバウンドの
**呼び出し箇所すべて**を grep します。

- HTTP クライアントのファサード/ライブラリ、生の `curl`、URL に対する `file_get_contents`/`fopen`、
  URL を受け付ける画像ライブラリ、PDF/HTML レンダラー、Webhook 送信処理、RSS/OG/リンクプレビューの
  フェッチャー、「URL からインポート」機能、ユーザーの URL を転送するサードパーティの
  「リーダー」/「スクリーンショット」サービス。
- **二次的なフェッチ**: 取得したばかりのページからサーバーが抽出する URL
  （スタイルシート、画像、リダイレクト、`<link>`、サイトマップのエントリ）。
  最初のホップは検証されていても、2番目は検証されていません。
- 保存された URL を後からジョブが使うもの（アバター URL、Webhook URL、コールバック URL）。
- サードパーティに*送る*もの: ユーザーが指定した URL を外部リーダーに転送することは、
  SSRF だけの問題ではなく、データ開示と信頼に関する判断です。
- **ヘッドレスブラウザ、PDF、スクリーンショットのレンダラー**がユーザー制御のURLやHTMLを読み込む場合: 自前のコード内でのIPピン留めは、ブラウザが取得するものまでは覆いません。ネットワーク層またはフィルタリングプロキシで外向き通信を制限し、`file://` へのアクセスと、可能ならJavaScriptも無効にします。**ブラインド**SSRF（応答が表示されない）には、*自分が所有する*アウトオブバンドのリスナーを使い、第三者のものは決して使いません。

## 2. ガードの設計（1つのコンポーネントにまとめ、すべてのシンクをそこ経由にする）

1. **スキーム**の許可リスト: `http`/`https` のみ。userinfo（`user:pass@`）、空白、
   バックスラッシュ、制御文字、ドットを含まない名前（`localhost`、単一ラベルのホスト）を拒否します。
2. **ポート**の許可リスト（例: 80/443）。これだけで、たまたま到達可能な内部アプリのポートを含め、
   多くの内部サービスを無効化できます。
3. **文字列ではなく、名前解決してから IP を判定する**。数値表記（`2130706433`、`0x7f.1`、`0177.0.0.1`、
   `127.1`）を正規化します。解決された*いずれかの*アドレスが非公開であれば拒否します。対象は
   ループバック、RFC1918、リンクローカル（クラウドメタデータ）、CGNAT `100.64/10`、`0/8`、
   マルチキャスト/予約済みです。IPv6 ではグローバルユニキャストのみを許可し、`::1`、リンクローカル、
   ユニークローカル、IPv4 マップ、6to4、NAT64 形式を拒否します。
4. **検証済みの部品から URL を再構築する**。元の文字列をクライアントに渡してはいけません
   （パーサーの解釈差: `http://a\@127.0.0.1`、`http://127.0.0.1#@example.com`）。
5. 接続には**検証済みの IP を固定（ピン留め）**します（例: curl の resolve オーバーライド）。
   これにより、2回目の DNS 応答で内部アドレスへ再バインドされることを防ぎます。
6. **リダイレクト**: 自動追従しません。ホップ数の上限を設けて手動で追従し、ホップごとに
   ガード全体を再実行します。
7. **TLS 検証を有効**にします。ガードを迂回する環境プロキシの利用は行いません。
8. 用途ごとの **Content-Type の許可リスト**（HTML、CSS、プレーンテキスト）と、転送を中断する
   シンクによって強制される**展開後サイズ**の上限（圧縮爆弾への防御。`Content-Length` の検査だけでは不十分）。
9. 接続と全体の**タイムアウト**。
10. **ユーザー向けのメッセージは汎用的**にします（「この URL は解析できません」）。理由とユーザー ID は
    ログに残し、**URL は残しません**。

## 3. 実行するテスト（すべて自分の検証用テナントに対して）

- 上記のすべての表記によるプライベートアドレスと特殊アドレス。IPv6 の各種形式。
- 自分が管理していて、プライベートアドレスに解決されるホスト名（DNS リバインディング、および
  「公開1つ+プライベート1つ」の A レコード）。
- プライベートアドレスへのリダイレクト、ホップ上限を超えるリダイレクトチェーン。
- スキーム/ポートを変更するリダイレクト。
- HTML 機能に対して返される非 HTML コンテンツ、上限を超えて展開される圧縮レスポンス、
  非常に遅いレスポンス。
- 二次的なフェッチ: スタイルシート/画像の URL がプライベートアドレスを指しているページ。
- **正の対照（成功するはずの対照リクエスト）**を確認する: 通常の公開 URL が引き続き動作すること。
- ブロックが、理由付きで、URL を含めずにログに記録されていることを確認する。

## 4. ローカル環境で実際のクライアントを動かせない場合 (FL-31)

ローカルのランタイムに、本番で使う HTTP 拡張がない場合は、本番ホスト上で**使い捨ての検証スクリプト（ハーネス）**を使って
ピン留めと中断の挙動をテストします。ループバックのテストサーバーと、ループバックの規則だけを緩める
ガードのサブクラスを用意します。確認項目は次のとおりです。ホスト名が解決できなくてもピン留めが機能すること、
サイズ超過の圧縮ボディがメモリを抑えたまま早期に中断されること、自己署名証明書が拒否されること、
プライベート範囲へのリダイレクトがブロックされること。終了後は、テストサーバーのポートが閉じていることを確認し
（組み込みサーバーは、親プロセスを kill しても生き残るワーカーを fork する場合があります）、
ハーネスを削除します。(FL-34)

## 5. 明記すべき残存リスク

- ガード付きフェッチは、*内容*が悪意あるものであることまでは防ぎません（安全にパースし、出力をサニタイズする）。
- URL をサードパーティのリーダーに転送すれば、その URL は依然として開示されます。
- 許可されたポート（80/443）で到達可能な内部サービスは引き続き対象範囲です。ネットワークも分離してください。
