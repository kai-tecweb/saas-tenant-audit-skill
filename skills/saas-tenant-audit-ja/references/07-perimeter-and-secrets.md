## オリジンの露出（CDN/WAF の迂回）

- オリジンサーバーに IP で直接到達し、CDN を迂回できるか。外部からテストします。
  オリジンのアドレスに対して 80/443 と、すべてのアプリポート（フレームワークの開発用/本番用ポート、
  管理パネル、データベース、キャッシュ）へ接続します。対象として指定されたホストと、よく知られたポートの短いリストだけを調べ、アドレス範囲のスイープはしません。到達できるべきでないものに到達できれば指摘事項です。
- 対策: 80/443 は CDN の範囲のみを許可するファイアウォールの許可リストとし、アプリポートは拒否します。
  CDN が新しい範囲を公開したときに範囲を更新する手順を文書化して維持します。SSH は、鍵を紛失しても
  使える方法で到達可能にしておきます（ホストアクセスを参照）。
- フレームワーク自身の公開ポートが、ポートの許可リスト（`05`）によって SSRF からはブロックされていても、
  直接露出の問題であることに変わりはないことに注意します。
- TLS モード: CDN→オリジン間が暗号化されているかを把握します。個人情報を扱うプロダクトは、
  平文で送るべきではありません。社内標準やベンダーの既定値が別の内容を定めている場合は、黙って逸脱せず、
  理由を付けた例外を記録します。（標準は既定値であり、判決ではありません。）

## 実クライアント IP (FL-20)

レート制限とログの質は、クライアント IP の質で決まります。方式を選ぶ前に、次を一覧にします。

1. 各ホップが、どのヘッダーを**設定する**のか、単に**素通しする**のか。
2. オリジンに直接到達できるか（できるなら、どのヘッダーも偽造できる）。
3. フレームワークの「信頼するプロキシ」オプションが何を信頼するか。

教科書的な「localhost からの forwarded-for ヘッダーを信頼する」は、プロキシがそれを上書きしない場合や
オリジンに直接到達できる場合には偽装可能です。より安全な方式は次のとおりです。*自前のプロキシ*が
ソケットのピアアドレスから書き込むヘッダーだけを信頼し、CDN のクライアント IP ヘッダーは、そのピアアドレスが
CDN の公開レンジ内にある場合にのみ信頼し、直近のピアがループバック/プライベートである場合にのみ動作させます。
実装前後の測定（保存された IP がプロキシのものだったが、今はクライアントのもの）と、偽造ヘッダー付きの
リクエストを**1回**（保存された IP は真のものであり続けなければならない）で証明します。取得したレンジ一覧を
連結するときは改行を正規化し、すべてのエントリを検証します。

設計上の帰結: 後でアプリのランタイムを別のサーバーの背後に移す場合は、「ピアがローカルのプロキシである」
ホップを維持してください。そうしないと信頼ロジックが壊れます。

## ヘッダーとフレーミング (FL-27, FL-13)

- トランスポートセキュリティのヘッダーは自社ドメインのみに付与します（管理していないテナントの
  独自ドメインには付与しません）。あわせて `nosniff`、妥当なリファラーポリシー、フレームポリシー
  （`X-Frame-Options` または CSP の `frame-ancestors`）を設定します。ただし、先の判断が後の機能を
  制約することを忘れないでください（埋め込み用の中継ページは、フレームポリシーが許可するホスト上に
  置く必要があります）。
- バージョンバナー（`Server`、`X-Powered-By`）を各ホップで削除または空にし、言語ランタイムの
  露出フラグも無効にします。
- ホスト名ごとの挙動: テナントのサブドメインと独自ドメインは、1つの server ブロックを共有していることが
  よくあります。マーケティングサイト向けに追加したリダイレクトや完全一致の `location /` が、
  すべてのテナントのルートページを黙って置き換えることがあります。ステータスコードが証明するのは到達性であって、
  同一性ではありません。apex、www、テナントのサブドメイン、独自ドメインについて、**コンテンツの同一性**
  （テナント固有のタイトル/テキスト）を確認します。(FL-13)

## デバッグ出力とエラー出力

- デバッグモードは本番で無効でなければなりません。エラーを発生させる**無害なリクエストを1回送って検証**します
  （不正な形式のパラメータを持つ存在しないルート）。デバッグページは、例外クラス、絶対パス、スタックトレースを
  開示します。エージェントと人間で評価が分かれることがありますが、確認用の GET を1回送れば決着します。(FL-26)
- 本番のログレベル: リクエストボディやトークンのデバッグレベルのログ出力がないか確認します。
  ログをローテーションし（日次で保持期間を設ける）、ディスクを埋めたり、データストアに成長したりしないようにします。
- API クライアント向けのエラーレスポンスは、汎用的で一貫したものにします。

## 内部専用エンドポイント

マシンの呼び出し元向けのエンドポイント（キャッシュ再検証、cron フック、ヘルス/メトリクス、フレームワークの
ビルド用エンドポイント）は、インターネットから到達できないようにします。外部からのリクエストはリバースプロキシで
ブロックします。**ブロックする前に、すべての呼び出し元を洗い出します (FL-21)**。自サーバーが公開 URL 経由で
自分自身を呼び出している場合も含まれます。まずそれらの呼び出し元を内部アドレスに切り替え、その後ブロックし、
内部経路が引き続き動作し、外部経路が 403/404 になることを確認します。

## ホストレベルのアクセス（明示的なスコープがある場合のみ）

- SSH: 鍵認証のみが理想ですが、パスワードログインを非常用の逃げ道（ブレークグラス）として意図的に残す場合
  （例: コンソールアクセスがない）は、理由を文書化し、補完策を講じます。強力なランダムパスワード、
  fail2ban 形式の遮断、root ログイン禁止、低い `MaxAuthTries` です。無条件に無効化を推奨しては**いけません**。
  多数の鍵をロードしている場合は `IdentitiesOnly` を使います。
- `sudoers`: コマンドは完全一致のリストとし、ワイルドカードは使いません。「パスワードなし」は、一覧表示ではなく、
  無害なコマンドを `sudo -n` で実行して証明します（`sudo -n -l` は「許可」と報告しますが、パスワード付きで許可される
  場合も含みます）。(FL-24)
- 特権を伴う変更: 認証済みのセッションを1つ開いたままにして安全網とし、リロード前に設定を検証し
  （`sshd -t`、`visudo -cf`、`nginx -t`）、進む前に**新しい**接続から確認します。ステップごとにレビュー済みの
  スクリプトを1つ用意し、ロールバックを最初に明記し、権限のない読み取りで検証します。どのマシンの、どのアカウントか
  を明示し、絶対パスを示します。(FL-32)

## シークレット衛生の棚卸し

合意したスコープの範囲内で、自分が所有する、または調査を許可されたシステムに限ります（他人のファイルやアカウントは対象外）。次を探します（報告するのは**件数、ファイル名、キー名のみ**です。値や一致した行は決して出さない、FL-23）。

- デプロイスクリプト、ドキュメント、運用手順書、シェル履歴、CI 設定、エディタの設定/許可リスト、
  チャットのエクスポート、AI アシスタントのメモリ/ログにある平文の認証情報。
- 作業ツリー内の `.env` のバックアップやコピーで、**未追跡だが ignore されていない**もの
  （コミット1回で公開されてしまう）— 稼働中のファイルとハッシュで比較します (FL-25)。
- git 履歴に現れるシークレット（HEAD から削除しても、ローテーションにはなりません）。
- 同じ値の複数サービスでの使い回し（システムアカウント、データベースの root、他のアプリ）。
- ファイルモード（`.env` は 600 であるべき）と、誰が読めるか。
- 公開が前提のビルド時公開変数（`NEXT_PUBLIC_*`、`VITE_*`）— シークレットが含まれていないことを確認します
  （バンドルに埋め込まれます）。

ローテーションが完了するのは、新しい値が機能し、古い値が**それが有効だった可能性のあるあらゆる場所で**拒否され、
保存されていたすべての場所が消去されたときだけです。作業を行うエージェントは、不要なシークレットを保持すべきではありません。
ユーザーには1行の対話的なコマンドを引き渡し、その後は読み取り専用で検証します。(FL-33)

## プロセススーパーバイザーと「停止した」サービス (FL-22)

「アプリを止める」には、複数の起動経路があることがよくあります。プロセスマネージャー、cron/タイマー、
systemd ユニット、コンテナの再起動ポリシー、デプロイフックです。すべてのスーパーバイザーを洗い出し、
それぞれを停止し、1ティック待って、もう一度確認します。また、デプロイスクリプトの**ヘルスチェック**も確認します。
自分が思っているのとは別のアプリケーションをテストしていた可能性があります。

## 変更の安全性

- ポートとプロセスマネージャー: ランタイムを入れ替える場合（開発用サーバー → 本番用アプリサーバー）は、
  プロキシがすでに使っているアドレスを維持し、新しいランタイムを並行するポートに置いて並べてテストし、
  ヘルスチェックが失敗したら自動でロールバックする形で切り替え、再起動で古いものが復活して衝突しないよう、
  検証後にのみ古いスーパーバイザーのエントリを削除します。(FL-35 notes)
- **公開している制限値**を、それを強制するサーバーに対して測定します（アップロード上限、ボディサイズ、
  タイムアウト）。開発用サーバーの ini が、検証ルールよりはるかに低い値で黙って上限をかけていることがあります。
  (FL-35)
