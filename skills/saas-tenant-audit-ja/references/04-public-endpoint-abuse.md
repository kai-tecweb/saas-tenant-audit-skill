# 04 — 公開エンドポイントの悪用、コスト、レート制限

目次: 脅威モデル · コスト発生箇所の棚卸し · 統制チェックリスト · ボット対策 ·
埋め込みウィジェット · クォータ · 副作用なしのテスト方法 · 制限では防げないもの

匿名エンドポイントや無料枠のエンドポイントは、次のような用途に転用され得ます。メールの中継、従量課金 API のメーター
（LLM・画像・音声）、ストレージの埋め尽くし、カードテストのオラクル、試用アカウントの大量作成です。
対策は多層で行います。監査では、各層が存在し、**実際に拒否するところが確認されていること**を検証します。(FL-11)

## 1. コストと副作用の発生箇所をすべて洗い出す

棚卸し（`01`）から、呼び出し側が対価を支払わずに次のことができるエンドポイントすべてに印を付けます。

- メール/SMS の送信（問い合わせフォーム、サインアップ確認、パスワードリセット、招待、
  オーナー通知）— 宛先を攻撃者が選べる場合があります。
- 有料ベンダーの呼び出し（LLM、画像生成、音声認識、地図、検索）。
- 永続データやファイルの作成（送信内容、アップロード、セッション、アカウント、試用）。
- 決済への関与（インテント作成、クーポン適用、購入の検証）。
- 重いジョブのエンキュー。

**認証済みの無料枠**ユーザーも確認します。メール確認済みのアカウントは有料アカウントではありません。

- **決済とインポートの整合性**（製品にある場合）: 金額と通貨を自前の記録とサーバー側で突き合わせる。決済イベントのリプレイ期間と、本番/テストモードの確認。スプレッドシートのインポート/エクスポートのサイズ上限と数式インジェクションの無害化（`=`、`+`、`-`、`@` で始まるセル）。アーカイブやアップロードの爆弾。

## 2. 統制チェックリスト（箇所ごと）

| 統制 | 確認内容 | 現場メモ |
|---|---|---|
| **実クライアント IP** をキーにしたレート制限 | リミッターは真のクライアントを見ているか、すべてのリクエストをプロキシのアドレスとして見ていないか | FL-20 |
| 有用な場合は複合キー | ログイン: 識別子+IP。1つの IP が多数の識別子に対して試行できないよう、IP 単位の上限も検討 | FL-16 |
| 匿名の書き込みに対する人間/ボット確認 | サーバー側での検証、ベンダー障害・設定不備時は**フェイルクローズ（安全側に倒す）**、トークンは使い捨てで用途（アクション）に紐づく | FL-14 |
| 有料呼び出しのテナント単位の月間クォータ | ガード自身がインクリメントするアトミックなカウンタ、失敗時のみ解放 | FL-11, FL-17 |

## 3. ボット対策の詳細 (FL-14)

- サーバーは**トークンを自ら検証**しなければならず、クライアントを信用してはいけません。トークンが欠落・無効・
  再利用済み・別アクション用のいずれの場合も拒否します（422/403）。ベンダーに到達できない場合や
  シークレットが未設定の場合は**拒否**します（フェイルクローズ、503）。許可してはいけません。
- ベンダー呼び出しの*前*にリミッターを適用し、無効なトークンでベンダーを叩き続けられないようにします。
- 両方の経路を意図的にテストします。
  - 失敗経路: トークンなし、偽トークン、再利用トークン、別アクション用のトークン。
  - 成功経路: 実ブラウザのセッションでのみ。自動化ツールから起動したブラウザは
    ウィジェットに（正しく）拒否されることが多いため、通常起動したブラウザにデバッグポート経由で
    接続して正常系を検証します。
- ウィジェットは shadow DOM/iframe の内側に描画されることが多いため、iframe のセレクタではなく、
  隠しレスポンス入力に対してアサートします。
- ウィジェットはドメインに紐づきます。テナントの**独自ドメイン**はウィジェットで許可されていない場合があります。
  許可されたホスト上の中継ページで、親オリジンを厳密に検査すれば（正確な親オリジンへの `postMessage`、
  nonce、登録済みドメインのみを対象にした `frame-ancestors`）、検査を緩めずに解決できます。
  先に取得したヘッダーを確認してください。フレーム拒否ポリシーが、中継ページを置ける場所を決めます。(FL-27)
- 順序: ウィジェットは送信のたびにリセットされなければなりません（トークンは使い捨てです）。
- ベンダーが公開しているテスト用キーが非本番環境に使えるなら、それを使います。テストするのは、監査を許可された対象のウィジェットだけです。

## 4. 埋め込みウィジェットとクロスオリジンでの利用 (FL-27)

テナントが埋め込むウィジェット（チャット、予約、フォーム）の場合:

- 作成されたセッションを、発行された**オリジン**に紐づけ、それ以外のオリジンには
  「存在しない」場合と同じレスポンスで拒否します。
- 有効化されていて、公開済み/未削除で、*かつ埋め込み元のページから参照されている*リソースのみを
  配信します。ID だけで利用できてはいけません。そうでないと、任意のサイト（や curl）が
  他テナントのウィジェットをそのテナントの課金で利用できてしまいます。
- 限界を正直に述べます。ブラウザ以外のクライアントは `Origin` を偽装できます。オリジン検査が防ぐのは、
  他の*サイト*がテナントのウィジェットを使うことです。スクリプトはボット検証、スロットル、クォータで止めます。
  公開ページに含まれるリソース ID は公開情報であり、隠すことに頼ってはいけません。

## 5. クォータ: 設計と検証

- (テナント, カウンタ, 期間) をキーにしたテーブルで数え、「最大 N 件」には**1つの条件付き UPDATE**
  （`used + n <= limit`）で消費します。「残りのうち最大 N 件を付与」には行ロックを使います。
  行はトランザクションの*外*で存在を保証します。(FL-17)
- デクリメントは失敗した試行に対してのみ行い、削除時には行いません。削除して再作成すると上限を回避できてしまいます。
- 既存の制限を強化する前に、**旧制限が本当に集計されていたことを証明**します。検証用テナントで上限を超えて
  リクエストし、保存された数値を読み戻します。マスアサインメント保護によって黙って落とされる列を
  合計している上限は、実質無制限です。(FL-11)
- 並列リクエストと素朴な対照（naive control）でテストします（`08` を参照）。

## 6. 副作用なしのテスト (FL-16)

- レート制限は**存在しない対象**で発動させます（リミッターが集計した後、メール/AI/決済の呼び出しの前に 404 を返す）。
- テストごとに一意の偽の識別子を使い、実アカウントがロックアウトされないようにします。
- 回復の測定: 分単位のリミッターは `Retry-After` を過ぎるまで待ちます。時間単位のものは、
  保存された有効期限を過去に動かして自然失効を再現し、その後キーを削除します。
- 作成したカウンタ、キャッシュキー、行をすべて削除します（ジョブが非同期に作成した行も含みます）。
  ベースラインと比較します。
- **自分の検証スクリプト（ハーネス）もリミッターの対象です**。セクションの間でカウンタをクリアしてください。
  また、共有キャッシュテーブルをクリアすると、テストに必要なセッションも消える場合があることに注意してください。
  (FL-09)
- これらの手順の一部（保存された有効期限を過去に動かす、カウンタやキャッシュキーを削除する、カウンタを読む）は、検証用環境のデータベースやホストへのアクセスが必要です。顧客レベルのアクセスしかない場合は、製品自身の削除/リセットのエンドポイントと新しい識別子を使い、クリーンアップや検証ができなかったことを一覧にします。

## 7. これらの統制では防げないもの（レポートに明記する）

- IP 単位の制限: 共有 NAT/CGNAT のバケット、分散した発信元、IPv6（/64 でグルーピング）。
- オリジン検査: ブラウザ以外のクライアントはヘッダーを偽装できる。
- 月間上限: 抑えられるのはコストであり、上限*内*での悪用ではありません。上限到達時のアラート/通知は
  別の統制です（イベントごとではなく、期間ごとに1回通知）。
- ボット確認: 有償の人間ソルバーが存在します。コストは上がりますが、悪用がなくなるわけではありません。
