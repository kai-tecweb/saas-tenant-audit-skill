# 06 — 認証、トークン、パスワードリセット、Webhook

目次: サインインとブルートフォース · パスワード規則 · リセットフロー · セッションとトークン ·
アカウント変更 · Webhook と外部イベント · シークレットとフェイルクローズ

## サインインとブルートフォース

- リミッターのキー: 識別子（正規化・小文字化）+ 実クライアント IP で、1分あたりの回数は控えめにします。
  **IP 単位の上限も併せて検討**してください。複合キーだけでは、1つの IP が多数の識別子に対して試行できます。
  残存リスク（共有 NAT、分散攻撃）を明記します。(FL-16, FL-20)
- 「不明なユーザー」と「パスワード誤り」で、汎用的な失敗メッセージと同じ応答時間にします。
- 攻撃者が被害者に対して発動できるロックアウトは、それ自体が DoS になります。アカウント全体の
  ロックアウトよりも、（識別子, IP）単位のスロットルを優先します。
- ログイン経路が実際にスロットルされていることを確認します（テストは新規エンドポイントしかカバーしていないことが多いです）。

## パスワード規則

- 最小長（12文字以上）とし、文字種の組成規則は要求しません。k-匿名性 API（ハッシュの先頭部分のみがサーバー外に出る）を
  使う漏洩パスワードサービスで照合します。短いタイムアウトを選び、失敗時の動作を明示的に決めます
  （可用性のため通常はフェイルオープンとし、文書化します）。
- サインアップ、変更、リセットで適用します。ログインでは再検証しません（既存ユーザーを強制的にロックしないため）。

## パスワードリセット（各項目をテストする）

- メールアドレスが存在してもしなくても、同じ応答と同程度の応答時間にします（未登録のアドレスでも同じハッシュ処理を行います）。
  メールはキュー経由で送信し、送信時間が見えないようにします。
- トークン: フレームワークのブローカーが生成し、ハッシュ化して保存し、有効期限は短く（例: 60分）、
  **1回限り**で、新しいリクエストで古いリンクを無効化します。
- 無効、期限切れ、メールアドレス不一致の場合は**同じ**エラーを返します。
- リセット成功時: 既存のセッション/トークンをすべて失効させ、必要に応じてアドレスを確認済みにし、パスワード規則を適用します。
- リクエストエンドポイントと消費エンドポイントは別々にレート制限します（IP+識別子単位と、IP 単位）。
- リセットリンクのホストは設定から取得し、リクエストの `Host` ヘッダーからは取得しません
  （ホストヘッダーポイズニング）。

## セッションと API トークン

- **設定の影響範囲 (FL-19)。** どちらも「トークンが失効する」と述べる2つの設定でも、動作は異なり得ます。
  すべてのトークンの作成時刻に対して評価されるグローバルな有効期限は、古いトークンをすべて一度に無効化します。
  トークン単位の `expires_at` は、新しく発行されたものにのみ適用されます。「これは既存のレコードに適用されるのか、
  新規のみか」を問い、要件に合う方式を選び、古いデータに似たフィクスチャ（ずっと前に作成され、有効期限なし）で証明します。
- 「他のデバイス」のテストを設計する前に、アプリ自身のセッションモデルを理解します。ログイン時にすべてのトークンを削除する
  （単一セッション）仕様の場合、「パスワード変更時に他を失効させる」テストは誤解を招きます。変更前にフィクスチャの状態を
  出力してください (FL-07)。
- 期限切れトークンは 401 を返し、クライアントはログインへリダイレクトしなければなりません（UI の経路もテストします）。
- 管理者/サービス用トークン: 全権限ではなくスコープ（abilities）を持たせ、期限切れトークンは定期的に削除します。
- ログアウトは、クライアント側だけでなく、サーバー側でも失効させます。

## アカウント変更

- メールアドレスの変更には現在のパスワードを必須とし、確認状態をリセットします。旧アドレスへの通知も検討します。
- パスワード変更時は他のセッションを失効させます。
- プロフィール更新でロール/テナント/プランのフィールドを受け付けてはいけません（マスアサインメント）。
- アカウント削除: 何を、いつ削除するのか、そして公開面が消えることを定義します
  （`03` のライフサイクル表）。

## Webhook と外部イベント (FL-18, FL-28, FL-30)

- **プロバイダー公式のルーチンによる署名検証を、フェイルクローズで行う。** 署名シークレットが未設定/空なら
  5xx で拒否します。多くのライブラリは空のキーでも平然と HMAC を計算するため、誰でも偽造できます。
  空のキーで計算した署名でテストします。
- 受信したままの**生ボディ**に対して検証します（JSON を再エンコードすると壊れます。プロキシはボディを
  書き換えてはいけません）。
- **冪等性**: イベント ID を保存し、`processed` のみを重複として扱います。`failed` のイベントと、
  `received` のまま古くなったイベントは再処理を許可します。同時の再配信は条件付き更新で守り、
  ちょうど1つのワーカーだけが進むようにします。
- **外部 ID をキーにするすべての更新に null ガードを入れる。** ID を抽出できない場合（プロバイダーが
  新しい API バージョンでフィールドを移動した場合）、ORM の `where(col, null)->update(...)` は
  `IS NULL` になり、*その列が空のすべての行*を更新します。実際に、これによって関係のない多数の行が一度に
  失敗状態に切り替わりました。ID が欠落/空の場合は早期にリターンし、フィールドが存在しない場合の
  テストを追加します。
- プロバイダーの API バージョンでフィールドは移動します。フォールバック付きで読み取り、スキップします
  （推測しません）。
- 購入/セッションが呼び出し元のテナントに属していることを検証します。所有者チェックの前に
  「記録済み → 成功」という分岐を置かないようにします（存在オラクル（存在有無が応答から推測できる状態））。
- テストイベントは、署名付きで無害なものだけを送り、後でイベントの行を削除します。可能な限り
  **実際の機能経路**を使います。DB を直接編集すると、実際の経路で露呈する前提条件が隠れてしまいます (FL-30)。

## シークレットとフェイルクローズの既定動作 (FL-18, FL-23)

- 設定されたシークレットに依存するすべての検査には、明示的な*空/未設定 → 拒否*の分岐と、
  空の値でのテストが必要です。
- 共有シークレットで保護された内部エンドポイント（キャッシュ再検証、cron トリガー、メトリクス）は、
  シークレット未設定なら 503、不一致なら 403 を返し、入力を厳密に検証し、さらに望ましくは、
  外部からまったく到達できないようにします（`07` を参照）。
- 許可リストの正規表現: 改行、NUL、Unicode、長すぎる入力でテストします。PHP では `$` は
  末尾の改行の手前にもマッチするため、`\z` を使います。明示的な文字クラスを優先します。
- 漏洩したシークレットのローテーションは、同じ文字列が有効になり得る**あらゆる保管先**（データベースの root、
  他のアプリ、トークン、デプロイスクリプト）で試して無効であることを確認し、書き込まれていた場所
  （履歴、ドキュメント、設定のバックアップ、チャットログ）から消去するまでは完了ではありません。
