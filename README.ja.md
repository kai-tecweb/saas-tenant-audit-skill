# saas-tenant-audit-skill

> [English](README.md) · **日本語**

**Laravel + Next.js で作られたマルチテナントSaaS**を、**他テナントのアカウントの視点**（ソースコードや内部情報なし）から
ブラックボックスで監査するための [Claude Code](https://claude.com/claude-code) スキル（SKILL.md形式）です。
実際の「監査→修正」の作業で**実際に踏んだ失敗パターン**を収録しています。

- 同じ内容のスキルが2つ: **`saas-tenant-audit`**（英語）と **`saas-tenant-audit-ja`**（日本語）。
- MITライセンス。**特定の顧客・案件に固有の情報は一切含みません**（抽象化した手順・チェックリスト・教訓のみ）。
- 問い合わせ・フィードバック: **X（旧Twitter） — https://x.com/iwasaki_dev40**

## なぜ、もう一つのセキュリティスキルなのか

公開されている多くのセキュリティスキルは、コードレビューや標準規格への分類が中心です。
このスキルは、調査した公開スキルに見当たらなかった次の3点を軸にしています（[docs/comparison.ja.md](docs/comparison.ja.md)）。

1. **第二テナントのブラックボックス視点。** あなたはテナントA（ふつうの顧客）です。パスのID、JSONボディのフィールド、
   保存された参照、存在オラクル、公開ウィジェット、匿名エンドポイントを通じて、テナントBのデータを
   読む・変える・推測できるかを試し、**被害側データが変わっていないことを前後のスナップショットで証明**します。
2. **実戦由来の失敗パターン。** 実際の監査で本当に起きた失敗を35件（`FL-01 … FL-35`）収録しています。
   例: `grep` を通したクリーンアップが致命的エラーを隠した／「何らかの拒否」を成功とみなしステータスコードを厳密に確認しなかった／
   処理が到達していないのに「発生しなかった」の確認が通った／古くなった回帰スクリプトが誤った結果を出した／
   検証スクリプト自身が対象のレート制限に引っかかった、など。
3. **Laravel + Next.js のマルチテナントSaaSに特化。** Sanctumのトークン有効期限の影響範囲、集計対象の列だけが
   マスアサインメントで黙って捨てられる問題、Route Handler/Server Actions が公開エンドポイントである点、
   ISR・サイトマップのキャッシュ無効化、ホスト名ベースの独自ドメインなど。手順そのものは他のスタックにも適用できるよう一般化しています。

## インストール

Claude Code は `~/.claude/skills/`（個人用）または `<プロジェクト>/.claude/skills/`（プロジェクト用）からスキルを読み込みます。

```bash
git clone <このリポジトリ>
cp -r saas-tenant-audit-skill/skills/saas-tenant-audit-ja ~/.claude/skills/
cp -r saas-tenant-audit-skill/skills/saas-tenant-audit    ~/.claude/skills/   # 任意（英語版）
```

使い方の例:

- 「このSaaSを他テナントの視点で監査して。ステージングのURLとテスト用アカウント2つはこれ」（最初にスコープと許可を確認します）
- 「このルート群について、2テナントの認可マトリクスを作って」
- 「私の検証・クリーンアップスクリプトを `09-harness-pitfalls` の落とし穴でレビューして」
- 「OWASP/CWEの対応付けと重大度つきで指摘事項の報告書を書いて」

## 実戦の教訓（概要）

詳細（症状 → 原因 → 対処）は `references/09-harness-pitfalls.md` にあります。

- **テスト設計（A）:** 期待値と実測値を1行に併記（FL-06）／前提条件をassert（FL-07）／「起きなかった」確認には正の対照（FL-08）／
  古い回帰スクリプト（FL-10）／既存の制御を改善する前にテスト（FL-11）／DB直編集でなく実際の機能経路（FL-30）。
- **テストデータの衛生（B）:** 失敗を隠さないクリーンアップ＝生の出力・接頭辞ベース・ベースライン一致（FL-05）／
  自分のトラフィックも対象の防御を受ける（FL-09）／ツールの問題が製品の不具合に見える（FL-12）／PIDで停止（FL-34）。
- **ツールと環境（C）:** ボット対策ウィジェットの検証（FL-14）／ローカルに拡張が無い場合（FL-31）／公称の上限を実測（FL-35）。
- **認可監査の方法（D）:** 3つのレンズ（FL-01）／JSON・保存フィールド内のID（FL-02）／存在オラクル（FL-03）／
  全エントリポイントで状態を確認（FL-04）／到達性は優先度を変える（FL-29）／ステータスコード≠正しい内容（FL-13）／
  エージェントごとの評価のばらつき（FL-26）／外部APIのフィールド移動（FL-28）。
- **セキュリティ設計（E）:** SSRFのシンク（FL-15）／副作用なしの上限テスト（FL-16）／並行処理の対照群（FL-17）／
  フェイルクローズと想定外の文字（FL-18）／設定変更の影響範囲（FL-19）／信頼するヘッダーの選び方（FL-20）／各制御の限界（FL-27）。
- **運用と引き継ぎ（F）:** 閉じる前に全呼び出し元を確認（FL-21）／「停止」＝起動経路が残っていない（FL-22）／漏えいした秘密（FL-23）／
  `sudo -n -l`（FL-24）／未追跡の秘密バックアップ（FL-25）／引き継ぎコマンド（FL-32）／不要な秘密は持たない（FL-33）。

## 規格との対応

指摘事項は**露出 × 影響**で順位付けし、OWASP Top 10のカテゴリ、OWASP API Security Top 10（2023）、主CWE 1つに対応付けます。
詳細は `references/10-reporting-and-severity.md`。CVSSベクターは任意です。

## 責任ある利用

**自分が所有する、または明示的に許可を得たシステム**が対象です。スキルは最初に許可の確認から始まり、検証用テナントと副作用のない対象を優先し、
秘密情報の出力を禁じ、攻撃用ツールを含みません。第三者のサービスや他の顧客のデータには使用しないでください。

## スクリプト

- `tenant_probe.py` — 2テナントのリクエストをJSONの計画から実行。1リクエスト1行で `expected=`/`actual=` を併記し、
  正の対照・「存在しないIDと同一か」の比較・被害側データのスナップショット差分を検査します。
- `selftest.sh` — プローブが「失敗できる」ことの証明（安全なモックは合格、脆弱なモックは失敗）。
- `leak_scan.sh` — 公開前の漏えいスキャン（秘密情報・公開IP・メールアドレス・独自の非公開語）。件数とファイル名のみ表示します。

どちらも「必ず失敗する」合成データ（わざと脆弱にしたモックサーバー、漏えいを仕込んだディレクトリ）で動作を確認済みです。
